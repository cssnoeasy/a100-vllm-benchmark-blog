# 服务化架构与能力边界

**状态：** 架构整理与有限工程验证  
**证据等级：** B/C  
**范围：** 从调用方、网关到推理服务的公开架构说明

## 1. 问题与边界

一个能够返回文本的推理接口，不等于已经成为可治理的服务。服务化需要明确调用方、网关策略、模型路由、推理引擎和监控之间的责任边界。第 5 周保留了配置驱动 vLLM runner 的实际记录，以及反向代理、鉴权、路由和用量记录相关的架构材料。本页只保留脱敏后的架构和已验证状态，不包含主机地址、账户、证书、密钥、防火墙规则或内部部署命令。

## 2. 请求链路

```text
调用方
  -> HTTPS 网关 / 反向代理
  -> 鉴权与模型授权
  -> 路由与请求策略
  -> OpenAI 兼容推理服务
  -> 调度器、Prefill、Decode、KV Cache
  -> 响应流

监控链路：网关与推理指标 -> Prometheus -> Grafana
实验链路：配置 -> runner -> manifest -> 校验 -> 汇总
```

主项目将直连 vLLM runner 作为已测量的性能路径。经过网关的请求会增加鉴权、网络、数据库或缓冲等开销，因此不能把直连 vLLM 的指标写成网关端到端指标。

## 3. 能力矩阵

| 能力 | 当前证据 | 可以公开的表述 | 当前边界 |
| --- | --- | --- | --- |
| 配置驱动的直连 vLLM runner | B | 已实际执行启动、就绪、热身、压测、归档、校验和质量检查 | 每次新运行仍需保留配置、manifest 与结果 |
| 就绪与提前退出识别 | B | 服务在就绪前退出可被识别和归档，不会长期停留在“启动中”状态 | 未分别覆盖网络和依赖故障 |
| 网关鉴权与模型授权 | C | 有架构和本地部署记录 | 缺少脱敏的有效 key、无效 key、未授权模型行为矩阵 |
| 反向代理流式转发 | C | 架构按流式转发设计 | 未单独验证首字节、断连和缓冲策略 |
| 用量记录 | C | 有数据库用量记录设计 | 未公开验证请求与记录的一一关联 |
| 限流与配额 | C | 有策略字段和 429 相关记录 | 未完成恢复窗口与并发公平性验证 |
| 请求取消 | D | 本项目尚未验证 | 不能声称已支持完整取消链路 |
| 重试 | D | 本项目尚未验证 | 流开始前后需要分开设计，不能自行假定安全 |
| 背压与过载准入 | B/C | 直连服务的受控过载已观察，网关准入未隔离验证 | 不把直连过载结果写成网关限流能力 |
| 优雅停机 | D | 尚未作为网关工作流验证 | 不能声称已完成请求排空与优雅重启 |

## 4. 已完成记录可支持的工程规则

1. 请求应有贯穿网关、推理服务、日志和指标的请求 ID。
2. 排队时间、TTFT、TPOT、总耗时、输入输出 token、状态、错误类别、路由与模型选择应分开记录。
3. 流式响应开始后不能任意重试，因为客户端可能已经收到部分 token，重试会造成重复内容或重复副作用。
4. 排队超时、首 token 超时、总请求超时、上游故障、鉴权失败、限流拒绝和客户端取消应使用不同错误类别。
5. 密钥只能通过环境变量或密钥管理机制提供；仓库只保留模板和占位符。

## 5. 已知未验证项

鉴权、模型授权、网关流式转发、用量记录、限流、取消、重试、背压和优雅停机均不能只凭架构图写成已完成能力。它们保留为已有部署材料的边界说明，不作为本项目新增实验成果。
