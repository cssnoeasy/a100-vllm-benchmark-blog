# 推理部署优化结果总览

> 证据等级：A（TP1/TP2 与 A100 量化正式实验）/ B（服务工程验证）/ C（框架选型和异构平台扩展）
>
> 本文只汇总已完成实验的结论，不包含新实验、外推估算或计划性结果。

## 1. 面向部署的决策问题

部署推理服务不是只选择一个框架或把模型成功启动。实际需要回答四个问题：

1. 在现有双 A100 拓扑下，单卡还是 TP2 更适合目标负载？
2. 显存紧张或并发提升时，应优先采用权重量化还是 KV Cache 精度策略？
3. 性能收益是否满足服务 SLO，质量代价是否可以由业务接受？
4. 得到结果后，如何让服务和实验可观测、可复现、可排障？

下表是本项目已完成证据所支持的部署决策，而不是不同硬件或不同模型之间的性能排名。

| 优化动作 | 对照基线 | 已验证结果 | 代价与边界 | 当前部署建议 |
| --- | --- | --- | --- | --- |
| 双卡张量并行（TP2） | 单卡 TP1，Qwen2.5-7B-Instruct，双 A100 80GB PCIe | 三类合成负载绝对吞吐提高 33.42% 至 44.71%；重负载 TPOT p99 降低 31.15%，E2E p99 降低 28.37% | 使用两张 GPU；轻负载 TTFT p50/p95 分别上升 5.43%/5.29%，短负载首轮约 8 秒级 TTFT p99 异常根因未证实 | 长输入、长输出、高并发负载优先纳入 TP2 候选；轻负载须以尾延迟和单位 GPU 成本复核，不能默认双卡更优 |
| BF16 + FP8 KV Cache | Qwen3-32B 的 BF16，单 A100 80GB，vLLM 0.19.0 | 模型加载显存不变，GPU KV token 容量从 39,200 增至 78,400；固定 500 题质量同为 83.60%；`512x256, c16` 输出吞吐从 264.83 到 267.69 tok/s | 与 Qwen2.5-7B 的 TP 实验不是同一模型；不是权重量化，不能释放权重显存；该负载吞吐仅约提高 1.1% | 当 Qwen3-32B 的 BF16 质量必须保持且瓶颈在 KV 容量时，作为低风险容量选项 |
| self W4A16 GPTQ 权重量化 | Qwen3-32B 的 BF16，单 A100 80GB，vLLM 0.19.0 | 模型加载显存从 61.03 GiB 降至 18.03 GiB，约降低 70.5%；GPU KV token 容量从 39,200 增至 215,344，约为 5.49 倍；`512x256, c16` 输出吞吐 312.90 tok/s，比 BF16 高约 18.1% | 固定 500 题总分从 83.60% 降至 77.60%，下降 6.0 个百分点；与官方 AWQ 只在部分负载更高，不能说全面更快 | 面向 Qwen3-32B 容量受限、且可接受该质量代价的业务；上线前必须保留业务质量门禁 |
| self W4A16 的 SLO 容量验证 | Qwen3-32B 在相同 SLO 下的 BF16，固定随机负载 | 在 `failed=0`、P99 TTFT 不高于 4000 ms、P99 TPOT 不高于 60 ms 的阶梯中，最高已验证点从 BF16 的 0.6 req/s 提高到 self W4A16 的 1.3 req/s；实际完成速率从 0.567 提高到 1.179 req/s | 仅适用于固定模型、硬件、请求长度和随机负载；1.4 req/s 时 self W4A16 的 P99 TPOT 为 60.95 ms，已越过门限 | 容量规划应以 SLO 下最高通过点为准，而不是只看峰值 tok/s |

## 2. 并行策略：TP2 的收益来自何处，何时不应使用

正式实验固定双 A100 80GB PCIe、无 NVLink、GPU 间 `SYS` 路径和跨 NUMA 条件，使用 Qwen2.5-7B-Instruct 与 vLLM `0.19.0`。TP1/TP2 在三类负载下各重复三次，共 18 轮、1,800 请求，所有请求成功。

- **收益**：TP2 的绝对吞吐提高 33.42% 至 44.71%；长输入、长输出、高并发负载下，TPOT p99 降低 31.15%，E2E p99 降低 28.37%。
- **代价**：TP2 占用两张 GPU，因此本实验没有证明单位 GPU 效率或成本更优。
- **反例**：长输入短输出中并发中，TP2 的 TTFT p50/p95 分别上升 5.43%/5.29%；短负载的 TPOT p99 上升 59.93%。首轮约 8 秒 TTFT p99 异常保留为未证实问题，不归因于 NCCL、NUMA 或任意单一因素。
- **工程判断**：并行度应由目标负载和 SLO 选择。重负载可用 TP2 换取绝对吞吐和尾延迟收益；交互式轻负载需要额外观测尾延迟，并与单卡策略共同评估。

完整条件、逐轮结果和异常审计见：[双 A100 TP1 vs TP2 正式基线](a100-tp1-vs-tp2-formal-baseline.md)。

## 3. 精度与容量策略：不能只展示显存节省

量化实验是独立的 Qwen3-32B 专题，将资源、性能、SLO 容量和固定集质量并列记录。四条路径均在单 A100 80GB 上使用 Qwen3-32B 与 vLLM `0.19.0` 完成统一矩阵；它与前文 Qwen2.5-7B 的 TP1/TP2 结果不构成同模型性能对照。固定质量集为 500 题，C-Eval 250 题与 CMMLU 250 题，`seed=20260804`、`temperature=0`、`max_tokens=8`，四条路径均完成 500/500 题。

| 路径 | 模型加载显存 | GPU KV tokens | `512x256, c16` 输出吞吐 | 固定 500 题总分 |
| --- | ---: | ---: | ---: | ---: |
| BF16 | 61.03 GiB | 39,200 | 264.83 tok/s | 83.60% |
| BF16 + FP8 KV Cache | 61.03 GiB | 78,400 | 267.69 tok/s | 83.60% |
| 官方 AWQ | 18.14 GiB | 214,272 | 303.52 tok/s | 82.20% |
| self W4A16 GPTQ | 18.03 GiB | 215,344 | 312.90 tok/s | 77.60% |

这里的核心结论不是“INT4 一定更快”。self W4A16 在此闭环并发负载中比 BF16 更快，但 c4/c8 下官方 AWQ 更高；资源接近也不等于质量相同。合理的部署流程是先以业务质量门禁划定可接受精度，再在该范围内用 SLO 阶梯确定容量。

完整参数、质量分歧和容量边界见：[A100 量化与容量规划](a100-quantization-capacity.md)。

## 4. 让优化结论可用：工程化证据

性能数字只有在实验条件可信时才有部署价值。已完成的 Benchmark 工程包括配置驱动运行、run ID、服务启动与 readiness 检查、热身、GPU/服务指标采集、结果归档、状态校验、汇总与质量门禁。它们提升的是结果的可复现性、可审计性和故障定位能力，不应被包装成额外的性能百分比。

已完成的服务侧验证包括 Prometheus/Grafana 与 GPU exporter、受控过载后的指标回落观察、推理进程退出后的重新 ready 和 smoke 验证，以及 60 分钟离线巡检文本回放。它们不等价于 admission control、网关级 timeout/cancellation/backpressure、OOM 自动恢复、多副本高可用或 Kubernetes 生产部署。

## 5. 扩展验证的正确位置

- **TensorRT-LLM**：Qwen3-32B BF16、A100 单卡、TensorRT-LLM `1.2.1` 的 PyTorch backend 在固定短负载下平均输出吞吐为 317.85 tok/s，vLLM 为 313.92 tok/s，差异约 1.25%。该结果只支持一次有限的部署选型验证，不支持 serialized TensorRT engine 性能结论或“TensorRT-LLM 全面更快”。
- **GB10 + llama.cpp**：ARM64 平台的 Qwen2.5-7B-Instruct GGUF `Q4_K_M` 已完成 CUDA 编译、冷启动、热请求、并发阶梯与短时连续请求验证，证明异构平台适配能力。它与 A100/vLLM 主线的模型、格式和软件栈不同，不进入上述优化排名。
- **QLoRA**：已完成训练和离线评测扩展，但尚未完成在线多 adapter serving，不作为当前推理部署优化成果。

## 6. 项目结论与待补证据

可以准确表述为：

> 我以部署决策而非单一峰值吞吐为目标，在双 A100 无 NVLink、跨 NUMA 条件下完成 TP1/TP2 正式基线，并在重负载中测到 TP2 的绝对吞吐提升 33.42% 至 44.71%。随后我对 A100 上的 BF16、FP8 KV Cache、AWQ 和自建 W4A16 路径同时评估了显存、KV 容量、SLO 下吞吐和 500 题质量。self W4A16 将模型加载显存降低约 70.5%，但质量下降 6.0 个百分点，因此我会按业务质量门禁决定是否部署，而不是只根据显存或峰值吞吐上线。

目前不能声称已完成：NCCL 通信占比量化、Nsight Systems 时间线分析、NUMA/CPU 亲和性对照、功耗与单位成本测量、完整网关服务治理、Kubernetes 部署、多副本高可用或真实机器人端到端压测。这些是后续可做的补证据方向，不能补写为既有成果。
