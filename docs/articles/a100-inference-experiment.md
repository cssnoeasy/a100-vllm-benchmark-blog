# A100 推理部署实验：从能跑到可解释的性能优化

## 1. 我想解决的问题

这组项目最开始的问题很朴素：Qwen2.5-7B 这类模型在单张 A100 80GB 上可以放下，那部署时还要不要开双卡 TP2？如果开了双卡，吞吐一定会更高吗？如果不开双卡，长上下文和高并发会不会吃亏？

后来实验逐步扩展成一条更完整的推理服务工程主线：部署 vLLM 服务，固定负载做基准测试，观察 TP1/TP2 的收益和反例，再继续补充显存预分配、KV Cache、量化、监控、过载恢复和业务回放。我的目标不是证明某个配置永远最好，而是把“怎么选配置”变成能被数据支撑的工程判断。

## 2. 硬件和软件边界

主线实验使用双 NVIDIA A100 80GB PCIe。两张 GPU 之间没有 NVLink，拓扑中 GPU 间连接显示为 `SYS`，这意味着多卡张量并行会遇到比 NVLink 机器更明显的跨卡通信成本。

正式 TP1/TP2 基线使用 Qwen2.5-7B-Instruct 和 vLLM 0.19.0。旧博客中曾记录过 vLLM 0.6.10 阶段的探索数据，这些内容现在只作为早期排查过程保留，不和正式基线混成同一组结论。

## 3. 正式基线：TP2 有收益，但不是“全面更快”

正式基线里，我把 TP1 和 TP2 放在同一硬件、同一模型、同一批负载下对照。实验覆盖三类合成负载，每类重复 3 轮，共 18 次运行、1800 个请求，全部成功，Preemption/Recompute 为 0。

从结果看，TP2 在三类负载中的绝对请求吞吐提升约 33.42% 到 44.71%。在长输入、长输出、高并发负载中，TP2 的收益更符合直觉：TPOT p99 降低 31.15%，E2E p99 降低 28.37%。这说明当计算量足够大时，两张卡确实能分摊一部分模型计算压力。

但这不是“多卡一定更好”。在长输入短输出负载中，TP2 的 TTFT p50/p95 分别上升 5.43% 和 5.29%；在短负载中，TP2 的 TPOT p99 上升 59.93%。短负载第一轮还出现过约 8 秒 TTFT p99 异常，TP1 和 TP2 都受影响，根因没有证实。

所以这组实验最适合写成：TP2 提高了本实验条件下的绝对吞吐，并改善了重负载尾延迟；但轻负载和首 token 延迟存在反例，不能宣称双卡全面更快，也不能宣称单位 GPU 效率更高。

## 4. gpu-memory-utilization：显存参数也要压测

旧博客补充实验里，我对 `--gpu-memory-utilization` 做过多值对比。条件是双 A100、Qwen2.5-7B、vLLM 0.19.0、TP2、2048/512 负载、100 个请求、最大并发 32。

结果比较清楚：0.70 时吞吐为 2.97 req/s，P99 TTFT 为 4779.35 ms；0.75 时吞吐达到 4.95 req/s，P99 TTFT 降到 519.54 ms；0.80 到 0.95 没有观察到额外收益。

这说明在这个场景下，显存预留太低会明显影响容量和排队；达到平台区之后，继续提高预留比例不一定提升吞吐。这个实验不能推出所有场景都应该设 0.75，但它说明我做过参数容量调节，不是只按默认值启动服务。

## 5. TP、PP 和通信排查

我也做过 TP2 和 PP2 的补充对比。在当时条件下，短文本场景 TP2 为 2.86 req/s，PP2 为 1.37 req/s；长文本场景 TP2 为 2.80 req/s，PP2 为 0.98 req/s。这个结果支持“本实验条件下 TP2 吞吐高于 PP2”，但不支持“TP 永远优于 PP”。

NCCL/NUMA 方面，我记录过 AllReduce 和 NUMA 绑定尝试：默认 P2P、关闭 P2P、显式 NUMA、interleave 的平均 bus bandwidth 都在约 11.3 到 11.45 GB/s 附近，差距很小。TP2 端到端吞吐曾出现约 2600 tok/s 和约 1500 tok/s 两种状态，但原因没有证实。

这部分更像工程排查笔记：先看拓扑，再看通信原语，再看 vLLM 端到端指标，最后结合系统日志。它不能写成某个 NCCL 参数的生产推荐，也不能把 IOMMU、VT-d 或 P2P 写成已证实根因。

## 6. Qwen3-32B 专题：FP8 KV Cache 和 W4A16 量化不是一回事

量化容量实验与前面的 Qwen2.5-7B TP1/TP2 正式基线使用不同模型。它在单张 A100 上使用 Qwen3-32B，沿用同一套“资源、性能、SLO、质量”评估方法，回答的是大模型容量与精度选择问题，而不是拿数值与 7B 的并行实验直接比较。这个专题里有两条容易混淆的优化线：FP8 KV Cache 和 W4A16 GPTQ。

FP8 KV Cache 主要影响 KV Cache 容量，不改变权重显存。Qwen3-32B 的 A100 量化容量实验中，BF16 的 GPU KV token 为 39,200；BF16 + FP8 KV Cache 提高到 78,400。固定 500 题质量上，BF16 和 BF16 + FP8 KV Cache 都是 83.60%。所以它适合写成 KV 容量策略，而不是权重量化，也不是已经证明所有负载都能加速的延迟优化。

self W4A16 GPTQ 则是权重量化。它把模型加载显存从 61.03 GiB 降到 18.03 GiB，GPU KV token 从 39,200 提高到 215,344，约 5.49 倍。在固定 SLO 阶梯里，最高已验证 request-rate 从 BF16 的 0.6 req/s 提高到 1.3 req/s。但代价也明显：固定 500 题质量从 83.60% 降到 77.60%，下降 6.0 个百分点。

这部分对部署岗位很重要，因为它不是单纯追求“更快”，而是在资源、吞吐、SLO 和质量之间做取舍。

## 7. 监控、过载和业务回放

只做离线 benchmark 不够，所以后面我补了可观测性和故障注入。项目里保留了 Prometheus、Grafana、GPU/System exporter、过载探针、进程退出恢复探针和 60 分钟巡检业务回放。

这里的边界需要写清楚：第 6 周短时 Smoke 不是 60 分钟长稳；巡检业务回放是离线文本推理回放，不是机器人端到端测试。它能证明 runner、场景数据、结果归档和质量门禁能跑通，但不能扩展成真实机器人线上闭环。

## 8. 我最终形成的部署判断

如果模型单卡能放下，我不会默认开 TP2，而是先按真实负载测 TP1 与 TP2。重负载下 TP2 可能带来更高绝对吞吐和更好的尾延迟；轻负载下，跨卡通信和调度开销可能抵消收益。

如果瓶颈是 KV 容量，优先看 `gpu-memory-utilization`、`max_model_len`、并发、FP8 KV Cache 等容量参数。如果瓶颈是权重显存或单机可承载请求率，再考虑 W4A16 等权重量化，但必须同时做质量回归。

如果性能出现波动，我会按硬件拓扑、NCCL 通信、vLLM 指标、系统日志和负载形态逐层排查。能确认的写成结论，只有迹象的写成观察，没验证的留在待办里。

## 9. 从一次压测到可复查的工程记录

性能数字本身不足以支持部署选择，因此我把正式实验整理成配置驱动的运行流程：生成 run ID，检查服务 ready，执行热身和冻结负载，保存 benchmark JSON、服务日志、GPU 采样与 vLLM metrics 前后快照，再由汇总脚本检查请求数、字段完整性和重复次数。异常也保留在结果中，例如短负载首轮的 TTFT p99 问题会单独审计，而不是从汇总中移除。

这套流程同样服务于量化与容量验证。对 Qwen3-32B 的不同精度路径，我不只比较单次吞吐，还同时查看模型加载显存、GPU KV token、固定负载和 SLO 阶梯，并将固定 500 题质量结果作为是否可用的约束。它把参数调整从“试到能跑”为止，变成一条能够追溯条件和代价的记录。

## 10. 主线之外的扩展验证

除 A100/vLLM 主线外，项目还保留了三组独立扩展材料。GB10 上的 llama.cpp 记录了 ARM64 环境中的编译、模型校验、冷启动、热请求、并发阶梯和短时连续请求；TensorRT-LLM 记录了单 A100、Qwen3-32B BF16、PyTorch backend 的固定短负载选型验证；QLoRA 则记录了将公开结构化维护事实转换为合成工单后的训练与离线评测迭代。

这些材料展示了平台适配、框架验证和模型适配的实际工作，但它们的硬件、模型、格式和任务不同。因此我将它们作为补充专题保留，不与 A100/vLLM 的正式性能线拼成同一张排名表。完整索引见 [项目总览](../../README.html)。

## 11. 还需要继续补的实验

现有内容已经能支撑“做过推理部署、基准测试、参数调优、量化容量、监控恢复和业务回放”这条主线。后续如果继续补强，我会优先做三类：真实业务流量分布下的 TP1/TP2 对照，更长时间的服务稳定性验证，以及量化方案在更多任务集上的质量回归。它们会让项目从“暑期主项目”更接近可长期维护的推理服务评估框架。
