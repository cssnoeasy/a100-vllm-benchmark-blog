# gpu-memory-utilization 参数补充实验记录

## 这组实验回答的问题

这组补充实验来自早期博客材料，主要回答一个部署问题：在双 A100 TP2、Qwen2.5-7B、vLLM 服务中，`--gpu-memory-utilization` 是否应该直接拉高到默认或接近满载，还是需要留出显存余量。

它不是新的实验，也不替代正式 TP1/TP2 基线。这里保留它，是因为它能说明我在推理部署中做过参数容量调节，并且用压测结果判断过“显存预分配”和“真实吞吐/尾延迟”的关系。

## 实验条件

| 项目 | 内容 |
| --- | --- |
| 硬件 | 双 NVIDIA A100 80GB PCIe |
| 模型 | Qwen2.5-7B-Instruct |
| 框架 | vLLM 0.19.0 |
| 并行方式 | TP2 |
| 负载 | 输入 2048 tokens，输出 512 tokens，100 个请求，最大并发 32 |
| 变量 | `--gpu-memory-utilization` = 0.70、0.75、0.80、0.85、0.90、0.95 |

## 观测结果

| gpu-memory-utilization | 吞吐 request/s | P99 TTFT |
| --- | ---: | ---: |
| 0.70 | 2.97 | 4779.35 ms |
| 0.75 | 4.95 | 519.54 ms |
| 0.80 | 与 0.75 接近 | 未观察到额外收益 |
| 0.85 | 与 0.75 接近 | 未观察到额外收益 |
| 0.90 | 与 0.75 接近 | 未观察到额外收益 |
| 0.95 | 与 0.75 接近 | 未观察到额外收益 |

这组数据里，0.70 的吞吐和 P99 TTFT 明显退化；从 0.75 开始，已观测指标进入平台区，继续提高到 0.80 以上没有看到稳定收益。

## 我如何解释这件事

vLLM 启动时会按 `gpu-memory-utilization` 预留一大块显存给 KV Cache。这个参数太低时，可用 KV block 变少，长输入和较高并发更容易进入排队状态，TTFT 会被放大。参数提高到足够支撑当前负载后，瓶颈可能转向计算、调度或通信，此时继续提高显存预留比例不会自然带来吞吐提升。

因此，这组实验支持的结论是：在本实验场景下，0.75 已经达到已观测性能平台；0.70 出现明显退化；0.80 到 0.95 没有观察到额外收益。

## 不能从这里推出什么

- 不能说所有模型和所有负载的最优值都是 0.75。
- 不能把 0.70 的退化单独归因于 Swap、Preemption 或某一个内部机制，因为当时没有直接采集足够的内部调度证据。
- 不能说更高的 utilization 一定会 OOM。它只是在工程上减少了显存余量，需要结合模型大小、`max_model_len`、并发和临时 buffer 观察。

## 工程实践要点

这组实验说明我没有只停留在“模型能启动”的层面，而是会把 vLLM 的显存预分配参数放进容量规划里测。面对长上下文或高并发业务，我会先用固定负载找出明显退化区间和平台区，再决定线上参数，而不是简单套默认值。
