# NCCL 通信排查笔记

## 记录目的

这份笔记把旧博客里的 NCCL 排查内容重新整理成公开项目可以接受的形式。它不是操作手册的最终推荐配置，而是记录我在多卡推理问题中会检查哪些层面、哪些证据能支撑判断、哪些内容还需要进一步验证。

## 排查顺序

1. 先确认硬件拓扑：使用 `nvidia-smi topo -m` 看 GPU 间是 NVLink、PIX、PHB 还是 SYS，并记录 CPU/NUMA 关系。
2. 再确认 NCCL 基础通信：用 AllReduce 等 micro benchmark 观察通信带宽和异常报错。
3. 再看 vLLM 端到端指标：分开观察 TTFT、TPOT、E2E、request throughput、token throughput 和失败请求。
4. 最后结合系统层日志：检查驱动、CUDA、进程退出、OOM、容器限制、服务重启和端口状态。

这个顺序的原因是，多卡推理性能不只由 NCCL 决定。NCCL 能说明通信层是否明显异常，但端到端性能还会被负载长度、batch、调度、KV Cache 和 CPU 侧服务开销影响。

## 可保留的工程动作

- 记录拓扑和版本，避免只写“用了两张 A100”。
- 用同一组负载固定变量，分别测试 TP1、TP2 或其他并行方式。
- 把 NCCL/NUMA 开关作为受控变量，不把一次尝试写成最终调优建议。
- 出现性能波动时，保留原始结果和未证实状态，不把所有波动解释成一个根因。

## 不在公开报告中写成已完成能力的内容

- `NCCL_TIMEOUT`、`NCCL_ASYNC_ERROR_HANDLING` 等环境变量可以作为排查方向，但如果没有故障注入验证，就不能写成已完成的生产自愈能力。
- systemd 自动重启、健康检查、Nginx 切流等内容，如果没有在本项目报告中闭环验证，就只写成后续治理方向。
- IOMMU、VT-d、P2P 相关配置如果没有明确对照和日志证据，就不能写成根因结论。

## 工程实践要点

这部分适合回答“你遇到性能波动怎么查”。我的做法是先把拓扑、通信、服务和负载拆开，不直接猜框架问题；每次只改一个变量，保留前后指标；最后把结论分成“能确认”“有迹象”“还没验证”三类。
