# 项目总线与技术决策

> 项目定位：大模型推理部署与性能优化工程项目。本文只组织已经完成的工作；计划项会明确标注，不把设计写成成果。

## 1. 一句话介绍

我围绕 vLLM 推理服务完成了一条从部署、基准测量、性能与容量优化，到可观测性、受控故障恢复和离线业务回放的工程链路。在双 A100 PCIe、无 NVLink 的环境中，我没有把多卡或量化当作默认答案，而是用冻结环境、重复运行、SLO 和固定质量集判断配置是否适合目标负载。

## 2. 要解决的工程问题

模型能够启动并不等于部署方案成立。这个项目回答四类实际问题：

1. 单卡 TP1 和双卡 TP2 在给定拓扑、模型与负载下，哪个更适合服务目标？
2. 显存与并发受限时，应该调整 KV Cache 容量，还是使用权重量化？质量代价是多少？
3. 性能数据如何做到可复现、可审计，并能够解释异常与失败样本？
4. 在压测、过载、推理进程退出和业务形态请求下，服务链路是否能被观测和重新验证？

## 3. 项目逻辑主线

```text
冻结环境与负载
    -> 部署 vLLM 服务并建立 TP1 基线
    -> TP1 / TP2 受控对照，按负载选择并行策略
    -> Qwen3-32B 的 FP8 KV Cache、W4A16 容量与质量取舍
    -> SLO 阶梯确定最高通过容量点
    -> runner、结果校验和质量门禁保证证据可审计
    -> Prometheus / Grafana、受控过载和进程恢复验证运行行为
    -> 60 分钟离线巡检文本回放验证业务形态输入
```

这不是若干框架或截图的并列清单。每一阶段都先定义问题和对照，再记录收益、资源代价、质量影响与未证实边界。

## 4. 已完成阶段与结果

| 阶段 | 做了什么 | 已有结果 | 证据与边界 |
| --- | --- | --- | --- |
| 1. 部署与基线 | 部署 Qwen2.5-7B-Instruct 与 vLLM，冻结模型、硬件、并行策略和三类合成负载 | 建立 TP1 / TP2 可重复的比较基础 | [正式基线](../a100-vllm-tp1-vs-tp2-baseline/)，A 级 |
| 2. 并行策略 | 在双 A100 80GB PCIe、无 NVLink、跨 NUMA 条件下，将 TP1 / TP2 各运行三轮 | TP2 绝对请求吞吐提高 33.42% 至 44.71%；重负载 TPOT p99 降低 31.15%，E2E p99 降低 28.37% | TP2 使用两张 GPU；轻负载尾延迟有反例，不能声称单位 GPU 效率或双卡全面更优 |
| 3. 参数与通信排查 | 对 `gpu-memory-utilization`、TP / PP、NCCL / NUMA、KV Cache 分配做补充记录 | 0.75 在指定负载达到已观测性能平台；TP2 在当时两组负载中吞吐高于 PP2 | [补充实验](reports/report-index.html) 为 B/C 级，未把单轮或未剖析现象写成通用结论 |
| 4. 容量与精度 | 在单 A100 的 Qwen3-32B 专题中比较 BF16、FP8 KV Cache、官方 AWQ 与 self W4A16 GPTQ 的显存、KV 容量、SLO 和固定质量集 | self W4A16 模型加载显存降低约 70.5%，GPU KV token 提高约 5.49 倍；SLO 下最高已验证 request-rate 从 0.6 提高到 1.3 req/s | 与 Qwen2.5-7B 的 TP 实验模型不同，不能做跨模型数值比较；self W4A16 固定 500 题质量下降 6.0 个百分点 |
| 5. Benchmark 工程化 | 实现配置驱动 runner、readiness 检查、运行 ID、校验、汇总、诊断与质量门禁 | 结果可保存运行状态、失败原因和指标完整性，避免只保留成功样本 | [工程化报告](reports/benchmark-engineering-results.html)，B 级；有限特性对照不作默认配置建议 |
| 6. 运行观测与恢复 | 接入 Prometheus、Grafana 和 GPU/System exporter；执行受控过载与进程退出后的重新 ready / smoke | 记录压力后指标回落与进程恢复后的服务就绪 | [过载与恢复](reports/04_Week6阶段B_PrometheusGrafana过载与恢复记录.html)，B 级，不等同高可用或 OOM 自动恢复 |
| 7. 业务形态验证 | 将巡检场景整理为脱敏的文本推理回放并运行 60 分钟 | 验证场景数据、回放客户端、结果归档与质量门禁链路 | [巡检回放](reports/inspection-replay-60m.html)，B 级，是离线文本回放，不是机器人端到端 |
| 8. 框架准入、异构部署与模型适配 | TensorRT-LLM 1.2.1 PyTorch backend 在单 A100、Qwen3-32B 的三轮短负载对照；GB10 ARM64 + llama.cpp GGUF 的编译、冷热、并发与约 20 分钟连续请求；QLoRA 合成工单的训练与离线评测；服务化架构与直连 runner 整理 | TensorRT-LLM 与 vLLM 的平均输出吞吐差约 1.25%，作为固定短负载选型参考；GB10 完成独立部署链路；QLoRA v3 留出合成文档 all-core 48/48、硬案例 6/8 | 不与 A100/vLLM 主线跨硬件、模型或格式排名；网关完整治理未验证；QLoRA 仍有 2 个严重 OCR 硬案例未通过，且不构成在线 adapter serving 结论 |

## 5. 核心结论与技术说明

### 项目摘要

我做的是大模型推理服务部署与性能优化。项目先在双 A100 上部署 Qwen2.5-7B 的 vLLM 服务，固定模型、GPU 拓扑、并行度和负载后比较单卡 TP1 与双卡 TP2。结果不是简单的“双卡更快”：TP2 在三类合成负载下绝对吞吐提高了 33.42% 到 44.71%，重负载的 TPOT p99 降低 31.15%，但轻负载尾延迟有反例，而且使用两张卡，所以我没有把它写成成本更优。另一个单 A100 的 Qwen3-32B 专题中，我把 BF16、FP8 KV Cache 和 W4A16 的显存、KV 容量、SLO 容量和 500 题质量一起评估。W4A16 把模型加载显存降低约 70.5%，但质量下降 6.0 个百分点，因此最终选择受业务质量门禁约束。两条实验线共享配置化 runner、指标采集、故障诊断和证据归档方法；我还补了 Prometheus/Grafana、受控过载和离线巡检回放，形成从性能数据到服务运行验证的闭环。

### 关键技术问题

| 技术问题 | 项目结论 |
| --- | --- |
| 为什么不是直接选择 TP2？ | 7B 模型单卡可放下，TP2 会引入跨卡通信并多占一张 GPU，必须用目标负载、尾延迟和成本口径验证。 |
| 量化的收益是什么？ | 资源收益和 SLO 容量都有量化，但质量出现 6.0 个百分点下降；因此量化是部署选项，不是无条件优化。 |
| 如何保证实验可信？ | 冻结环境和负载，重复运行，保留 run ID、配置、状态、原始结果、采样指标、失败记录与汇总逻辑。 |
| 遇到性能波动怎么办？ | 从负载形态、GPU 拓扑、NCCL 原语、vLLM 指标和系统日志分层排查；未被对照和 profiling 证实的内容只保留为观察。 |
| 服务是否生产就绪？ | 当前完成的是受控工程验证，不宣称 Kubernetes、多副本高可用、网关治理、OOM 自动恢复或机器人端到端已完成。 |

## 7. 当前边界与后续计划

以下内容没有被补写为既有成果：NCCL 通信时间占比、Nsight Systems 时间线、NUMA/CPU 亲和性严格对照、功耗与单位成本、Kubernetes、多副本高可用、网关级背压与取消、OOM 自动恢复、真实线上流量和机器人端到端测试。

后续若继续补强，应优先增加真实业务负载下 TP1 / TP2 对照、功耗与单位 GPU 吞吐口径、量化在更多业务任务集上的质量回归，以及更长时间且定义明确的稳定性验证。每项新工作应新增独立配置、原始结果和报告，不覆盖当前证据。
