# 从 Transformer 到推理服务

> 本文用于解释本项目的指标和工程选择。公式、机制和示意用于建立概念，不是本项目的实验结果；实验事实以各正式报告中的环境、负载和结果表为准。

## 1. 为什么从模型结构讲到服务指标

用户看到的是一次文本请求，推理服务实际要完成一条更长的链路：文本先被切分为 token，token 变为向量，经过多层 Transformer 计算，再逐个生成输出 token。在线服务还要处理排队、批处理、显存分配、请求取消和错误恢复。

因此，“模型能回答”只是起点。服务工程还需要回答：首个 token 要等多久、后续 token 输出是否稳定、并发升高后会发生什么、显存为何被占用，以及服务在压力或进程退出后能否恢复。

## 2. Token 与 Embedding：文本如何进入模型

模型不直接处理汉字或英文单词，而是处理 token ID。Tokenizer 将输入文本切分为 token；Embedding 层再把每个 token ID 查表转换为向量。输入长度越长，后续 Attention 需要处理的历史位置越多，Prefill 阶段的计算和显存压力也随之上升。

对服务而言，必须同时记录输入 token、输出 token 和并发，而不能只写“请求数”。同样是 100 个请求，`512 input / 128 output` 与 `2048 input / 512 output` 对调度器和 KV Cache 的压力完全不同。

## 3. Attention：当前 token 如何读取上下文

自注意力的核心是让当前位置与上下文位置建立关联。每个 token 会产生 Query、Key 和 Value：Query 用于发问，Key 用于匹配，Value 是被聚合的信息。简化地说：

```text
Attention(Q, K, V) = softmax(QK^T / sqrt(d))V
```

这意味着生成新 token 时需要访问之前 token 的 Key/Value。若每一步都重新计算完整历史，生成长度一增加，重复计算会迅速累积。KV Cache 就是为避免这部分重复工作而出现的。

## 4. Transformer Block：一次前向计算包含什么

典型 Transformer Block 可理解为两类主要计算：

1. Attention：从上下文中选择和聚合信息。
2. MLP：对每个位置的表示进行非线性变换。

残差连接和归一化使多层网络可以稳定叠加。服务侧无需把每一层公式都展开，但要知道模型层数、隐藏维度、注意力头数和 KV head 数会共同影响权重显存、KV Cache 大小和计算量。GQA/MQA 通过减少 KV head 数量降低缓存压力，是长上下文 Serving 中的重要设计。

## 5. Prefill：先处理整段输入

Prefill 指模型一次性处理用户已经提供的 prompt，并建立该 prompt 对应的 KV Cache。它通常计算密集、并行度较高，主要影响首个 token 出现前的等待时间。

服务指标中，TTFT（Time To First Token）近似覆盖排队、调度和 Prefill，再加上首个输出 token 的产生时间。它不是纯模型算力指标：高并发时，前面的请求、调度策略和显存预算都会抬高 TTFT。

本项目双 A100 TP1/TP2 正式基线和第 6 周过载记录均分别保留了 TTFT。读这些数字时，应始终同时看输入长度、并发和是否存在排队，不能把它直接等同于“模型首 token 算得多快”。

## 6. Decode：逐 token 生成输出

自回归模型每次只产生一个新的 token，并把它追加回上下文，然后继续下一步。这个阶段称为 Decode。由于一次通常只计算少量新 token，GPU 的并行利用方式与 Prefill 不同，常常更容易受批处理规模、调度和内存访问影响。

TPOT（Time Per Output Token）描述相邻输出 token 的时间间隔，适合观察解码阶段的用户可感知流畅度。E2E（端到端耗时）则覆盖完整请求，既包含 TTFT，也包含所有 Decode 时间。三者不能相互替代：

```text
E2E ~= 排队时间 + Prefill + 首 token + 后续 Decode
TTFT ~= 排队时间 + Prefill + 首 token
TPOT ~= 后续 Decode 的单 token 间隔
```

上式是解释关系，不是严格的统一测量公式；不同客户端、流式协议和统计实现的边界可能不同。

## 7. KV Cache：用显存换取重复计算的减少

Prefill 后，每层 Attention 的 Key/Value 会被保存。Decode 时只为新 token 计算新的 K/V，再读取历史缓存，这就是 KV Cache。它显著减少重复 Attention 计算，却带来明确的容量约束：

```text
KV Cache 占用与层数、KV 头数、head 维度、token 数、并发请求数和数据类型相关。
```

所以更长输入、更长输出和更多并发请求会同时推高缓存使用量。显存不是只装模型权重，还要容纳 KV Cache、运行时工作区和可能的图捕获或通信缓冲区。A100 量化专题中“权重显存下降”并不自动等于“服务质量不受影响”，正是这个原因。

## 8. PagedAttention：为什么要分页管理缓存

传统连续内存分配容易因为不同长度的请求产生碎片，也不利于回收。PagedAttention 将 KV Cache 切成固定大小的逻辑块，由 block table 将请求的逻辑 token 位置映射到物理块。

这种设计的工程价值是：请求可以按需获得块，完成后归还块；调度器更容易在有限显存内安排多个不同长度的请求；共享前缀也有机会复用已有块。它不保证所有负载下都更快，但解释了 vLLM 为什么能把 KV Cache 管理纳入调度决策。

## 9. 连续批处理：吞吐与等待如何同时出现

静态 batch 需要等待一批请求一起完成，在线请求的到达和结束却不整齐。连续批处理允许已经完成的请求离开 batch，新请求在合适时机加入，从而提高 GPU 利用率。

代价是调度目标出现张力：更积极地积累 batch 往往有利于总吞吐，却可能增加队列等待和 TTFT。第 6 周的受控过载验证正体现了这种边界：高并发负载下输出吞吐升高，但 P99 TTFT 和 P99 TPOT 同时变差。该结论只适用于报告中的固定模型、负载和环境，不是所有 Serving 系统的普遍数值规律。

## 10. Prefix Caching：相同前缀可以少做哪些工作

当多个请求共享系统提示词、文档开头或其他长前缀时，服务可尝试复用前缀对应的 KV Cache，减少重复 Prefill。是否真正受益依赖于请求组成、缓存命中、块管理、显存压力和调度时机。

本项目保留了 Prefix Caching 的重复观察记录，但没有严格同口径的关闭对照。因此它只证明“已记录该特性在既有负载下的行为”，不能写成“Prefix Caching 必然提升性能”。概念机制和某一次观察结果必须分开表达。

## 11. 从指标回到项目实验

| 概念 | 服务侧影响 | 本项目的对应证据 |
| --- | --- | --- |
| Prefill | 输入越长、排队越多，TTFT 越可能上升 | 双 A100 正式基线；第 6 周过载报告 |
| Decode | 影响流式输出节奏和 TPOT | 双 A100 正式基线；60 分钟巡检回放 |
| KV Cache | 影响并发容量、抢占和显存预算 | vLLM 指标、容量规划与量化专题 |
| 连续批处理 | 提高吞吐，也可能抬高尾延迟 | 第 6 周中等负载/高并发/恢复对照 |
| Prefix Caching | 共享前缀下可能减少重复 Prefill | Benchmark 工程化报告中的有限记录 |
| 进程与监控 | 决定运行状态能否被观测和恢复被验证 | Prometheus/Grafana、进程恢复复盘 |

## 12. 阅读结果时的四个检查点

1. 先看模型、硬件、版本、量化格式和并行策略是否一致。
2. 再看输入/输出长度、并发、请求数、热身和重复次数是否一致。
3. 将吞吐、TTFT、TPOT、E2E 和成功率分开阅读，不用单一数字概括服务质量。
4. 区分概念解释、工程验证和正式受控实验，不把有限观察扩大为通用结论。
