# 实验数据归档结构

本项目使用结构化归档来连接实验配置、运行结果、派生汇总和报告结论。它的目标不是让任意机器直接复跑历史实验，而是让读者可以核对“某个数字来自哪一次运行、采用什么口径、是否经过校验”。

## 1. 单次运行归档

每次实验运行建议归档到：

```text
results/runs/<run_id>/
```

`<run_id>` 应能区分引擎、模型、并行方式、负载和重复次数，例如 `a100_vllm_tp2_long_r2`。每个目录至少应包含以下逻辑内容：

| 内容 | 作用 | 是否公开迁入 |
| --- | --- | --- |
| 冻结配置 | 模型、引擎、并行、请求负载、热身和阈值 | 可脱敏后迁入 |
| 环境清单 | GPU、驱动、CUDA、框架和依赖版本 | 可脱敏后迁入 |
| 原始结果 | 请求数量、成功失败、延迟、吞吐和错误分类 | 仅迁入可公开汇总或必要样本 |
| 校验结果 | 结构校验、阈值检查、状态和失败原因 | 可迁入 |
| 派生汇总 | 重复运行的均值、分位数和对照差异 | 可迁入 |

模型权重、原始请求正文、完整服务日志、虚拟环境、内网地址和凭据不属于公开归档内容。

## 2. 关键字段口径

| 字段 | 含义 |
| --- | --- |
| `run_id` | 本次运行的唯一标识，应能关联配置、环境和结果。 |
| `status` | 运行状态，例如 `validated`、`warn`、`failed` 或 `skipped`。状态不是性能指标，不能省略失败记录。 |
| `requests_total` | 已提交请求总数。 |
| `requests_success` | 成功完成且符合本次成功定义的请求数。 |
| `requests_failed` | 请求失败数，须保留错误类别或失败原因。 |
| `input_tokens` / `output_tokens` | 负载的输入和输出 token 规模，解释吞吐和延迟时必须同时引用。 |
| `concurrency` | 最大并发请求数。 |
| `ttft_ms` | 从发送请求到收到首个流式 token 的时间；只适用于流式响应。 |
| `tpot_ms` | 后续输出 token 的时间间隔，用于观察解码阶段。 |
| `e2e_ms` | 完整请求端到端耗时，不能与 TPOT 混用。 |
| `throughput_tok_s` | 在声明的输入或输出口径下计算的 token 吞吐，报告必须标明分子。 |

## 3. 公开摘要与原始数据的关系

`results/manifests/` 保存可公开的配置、环境和汇总清单；`results/published/` 保存可被文章直接引用的审查后摘要。报告中的表格、图片和结论应回链至二者之一，或者明确标注其来自对应的正式报告。

公开摘要不能替代原始证据。它只保留支持当前结论所必需的数字、口径、质量门禁与局限。不同模型、硬件、引擎或量化格式的结果必须分组保存，不可因字段名称相同就并入同一排名表。

## 4. 发布前核对

发布任何一轮结果前，至少核对：

1. 配置、环境、结果和汇总使用同一个 `run_id` 或可追溯的关联关系。
2. 请求数、成功数、失败数与成功率能相互计算验证。
3. 延迟单位统一为毫秒，吞吐单位统一为 `tok/s`，并写清输入或输出口径。
4. `WARN`、`SKIP`、`failed` 和未证实根因不得在汇总时被删除。
5. 公开文本、截图和 manifest 不含真实服务器地址、用户名、绝对服务器路径、密钥或原始请求内容。
