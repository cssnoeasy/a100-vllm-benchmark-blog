# Benchmark 方法

## 1. 目标

本项目把 benchmark 用作部署决策的测量工具，而不只是输出一个峰值吞吐。每次对照先明确要回答的问题，例如 TP1 与 TP2 的取舍、KV Cache 容量策略，或量化后的 SLO 容量；随后将模型、服务参数和负载固定，再比较资源、性能和质量结果。

正式基准开始前必须冻结模型 revision、权重精度、KV Cache dtype、GPU 可见性、并行策略、最大上下文、显存比例、随机种子、负载长度、并发定义和重复次数。不同模型、硬件、量化格式或软件栈的结果保留为独立专题，不直接拼成性能排名。

## 2. 一次运行的流程

1. 由配置文件生成运行参数和 run ID，记录环境、模型、硬件可见性及负载定义。
2. 启动服务并完成 readiness 检查；服务未就绪不进入正式计时。
3. 先执行热身请求，再运行冻结的正式负载；并发、输入输出长度和请求数量均由配置控制。
4. 运行前后采集 vLLM metrics、GPU 采样和服务日志；结束后保存 benchmark JSON、退出状态及结果清单。
5. 汇总器校验字段完整性、成功请求数、缺失值、counter 增量和重复次数，再生成可供报告引用的聚合结果。

这样保留的不是一张图或一行结论，而是可以回到配置、原始结果和运行状态核对的证据链。目录约定见 [数据与结果目录约定](data_schema.md)，工程实现与已完成验证见 [Benchmark 工程化与已完成特性验证](../reports/benchmark-engineering-results.md)。

## 3. 指标口径

| 指标 | 本项目中的含义 | 使用方式 |
| --- | --- | --- |
| 请求吞吐 | 单位时间内完成的有效请求数 | 用于观察服务在固定负载下的完成能力 |
| 输出吞吐 | 单位时间生成的输出 token 数 | 结合请求长度解读，不能替代请求吞吐 |
| TTFT | 客户端收到首个非空输出的时间 | 反映排队、Prefill 和首 token 路径的综合等待 |
| TPOT | 相邻输出 token 的时间间隔 | 用于观察流式 Decode 阶段的尾延迟 |
| E2E | 从发送请求到完整响应结束的时间 | 用于判断用户侧完整等待时间 |
| 显存与 GPU KV token | 模型加载后的资源占用和可分配 KV 容量 | 用于容量规划，不能单独代表延迟收益 |
| 成功率与业务解析率 | HTTP 请求成功及输出满足业务 schema 的比例 | 回放任务中两项分别校验，HTTP 成功不等于结果有效 |

报告同时给出吞吐、TTFT、TPOT、E2E、GPU 利用率、显存或 KV Cache 和错误率。平均值不能替代 p50/p95/p99；多轮分位数如何聚合必须在对应报告中写明。

## 4. 异常与质量门禁

出现首轮异常、波动或失败时，原始记录保留在结果中，并单独做位置效应或日志审计，不事后删除数据来改善结论。量化专题除服务指标外，还对固定质量集运行质量门禁；容量结论以满足既定成功率、TTFT 和 TPOT 门限的最高通过点为准，而不是以单次峰值 token/s 代替。

## 5. 已完成范围

当前 TP1/TP2 正式示例覆盖三类合成负载、每组 3 次，共 18 轮和 1,800 个请求。Qwen3-32B 专题在单 A100 上将 BF16、FP8 KV Cache、AWQ 与 self W4A16 放入显存、KV 容量、固定负载、SLO 阶梯和 500 题质量闭环中评估。

这些记录建立了受控压力下的性能基线，但尚未覆盖 KV Cache 饱和、NCCL kernel 时间分解、功耗与单位成本、真实生产流量或完整网关调用路径。各专题的具体条件和结果应以正式报告为准。
